# 设计取舍

这份文档记录 ParcelMate 在几个关键岔路口**为什么选了 A 不选 B**。
面试时被问"你为什么这么设计"，答案在这里；自己回头看，也免得忘了当初的约束。

一句话前提：**这是个给宿舍 6 个人用的工具，不是给 6000 个人用的系统。**
所有取舍都从这条出发——先能跑、真有人用，再谈扩展。

---

## 1. 为什么不做账号体系，用「房间码 + 昵称」

**做了什么**：第一个人建房，系统生成 6 位房间码（如 `JCXMQZ`）；室友输入房间码 + 昵称就进去了，服务端种一个 cookie 记住身份。

**为什么不注册登录**：

- 目标用户就是同宿舍 6 个人，彼此认识。注册要手机号/邮箱、要密码找回、要防撞库——一整套成本换来的安全性，在这 6 个人之间并不存在。
- 真正的使用场景是"群里丢一句：房间码 JCXMQZ，都进来"。多一步注册，就少一半人进来。**降低第一次使用的摩擦，比补齐账号体系更能让项目活下来。**

**代价与兜底**：

- 换设备 / 清 cookie 就"掉出房间"，重新输一次房间码即可，成本可接受；
- 昵称在房间内唯一，重名会被拒（400），避免"小明帮你取件"分不清是哪个小明；
- 房间码从 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` 取（去掉了 0/O、1/I 这种念出来会听错的字符），6 位约 8.9 亿组合，猜码不现实。

**如果要做大**，演进路径是：房间码 → 微信小程序登录（openid 天然是账号）→ 保留房间码作为"加入房间"的入口。数据结构已经按这个留了口子：`member` 表外键指向 `room`，加账号体系只是给 member 加个 `openid` 列。

## 2. 为什么取件码明文存，只做"看不到"

**做了什么**：取件码原样存在 `parcel.pickup_code`，但在返回给前端时过滤——只有**发布者**和**接单人**能看到，其他房间成员拿到 `null`。

```java
boolean canSeeCode = p.ownerId() == viewerId
        || (p.takerId() != null && p.takerId() == viewerId);
```

**为什么不加密**：

- 取件码本身不是机密凭证，它是"一次性、限时、还要配合手机号后四位"的取件凭据；
- 如果加密存储，接单人就需要解密能力，密钥最终还是得发给前端——**加密只是把明文换了个地方放**，安全性没有实质提升，反而多了密钥管理。

**真正要防的威胁**是"同宿舍之外的旁观者看到取件码去冒领"，所以控制的是**可见范围**，而不是存储形态。这条边界写在代码里（`ParcelService.toViews`），也是这个项目里唯一涉及隐私的逻辑。

**什么情况下必须改**：如果要接校外用户、或者存身份证/手机号，那就必须上字段级加密 + 审计日志——那时场景已经不是宿舍了。

## 3. 为什么用 SQLite 而不是 MySQL

| 判断维度 | SQLite | MySQL |
| --- | --- | --- |
| 安装/运维 | 一个文件，随程序走 | 要装服务、建库、配账号、备份 |
| 数据量级 | 6 人 × 每天几单，一年不到 1 万行 | 完全过剩 |
| 部署成本 | 单文件挂载卷即可 | 额外一个容器 / 云数据库（要钱） |
| 并发 | 单写者，`maximum-pool-size=1` 足够 | 需要时才体现价值 |

**关键约束是部署**：一期目标是把项目挂到公网，让室友用手机打开。Render 免费档 / 10 元学生机上，多一个 MySQL 就多一份会挂掉的东西。SQLite 让"部署"退化成"启动一个 jar"。

**已经为迁移留好的路**：所有 SQL 都在 `repo/` 层手写，没有用到 SQLite 特有语法；连接串、驱动、初始化脚本集中在 `application.properties` 和 `schema.sql`。真要迁 MySQL，改三处配置 + 重新灌一遍 schema 即可。

**已知天花板**：SQLite 同时只允许一个写者。所以连接池刻意配成 1，把并发压到应用层排队——**这是刻意的取舍，不是疏忽**。真到写不过来的量级，说明这个项目已经不是"宿舍工具"了。

## 4. 为什么用 Spring JDBC + 手写 SQL，不用 JPA / MyBatis

- 项目作者的求职方向是 Java 后端，**SQL 是必须写熟的基本功**。用 JPA 会把这个练习机会自动生成掉；
- 这个系统的核心卖点恰恰是**一条手写 SQL**（版本号乐观锁，见下节）。ORM 把这条 SQL 藏进 `@Version` 注解里，讲故事的时候就少了一半；
- 数据模型只有 5 张表，没有复杂的对象图，`JdbcTemplate` 的样板代码量完全可控。

**代价**：多了些手写 row mapper。换来的是"每一条 SQL 我都知道它在干什么"。

## 5. 为什么用版本号乐观锁，不用悲观锁 / synchronized

```sql
UPDATE parcel
   SET status = 'TAKEN', taker_id = ?, version = version + 1
 WHERE id = ? AND status = 'OPEN' AND version = ?
```

**要解决的问题**：两个人同时点"接单"，不能让两个人都接到同一张单。

**为什么不是 `SELECT ... FOR UPDATE`**（悲观锁）：

- SQLite 没有行级锁，也没有 `FOR UPDATE`；
- 即便在 MySQL 上，悲观锁也要持有事务到提交，为一个"点一下就完事"的操作引入事务持有时间，收益很低。

**为什么不是 `synchronized`**：

- 它只在**单实例**内有效。项目现在是一个实例，但部署到 Render 后一旦扩容、或者以后开两个进程，锁就失效了，而代码看起来还是"对的"——这是最危险的一类 bug：**本地测试永远通过，上线后偶发双接单**；
- JVM 锁把"并发控制"放在了错误的层：真正共享的状态在数据库里，就该在数据库里解决。

**为什么乐观锁最合适**：

- 冲突概率极低（同一张单被两个人同时抢，一天可能一次都没有），为低概率事件加锁不划算；
- 一条 SQL 原子完成"检查 + 更新"，受影响行数 = 1 才算成功，失败就是"手慢了"，前端给个友好提示即可；
- 版本号还顺便提供了**状态机防护**：`transit(parcelId, from, to, expectedVersion)` 用同样的手法保证"已取 → 已送达"不会被乱序推进。

**关键纪律**：**绝不能**先 `SELECT` 查状态、再 `UPDATE`。中间那几毫秒足够别人插队——这正是 `ParcelService.take` 注释里写明的"坑"。

## 6. 为什么前端用原生 JS，不上 Vue / React

- 页面就 4 个 tab + 一个发布弹层，组件化收益极低；
- 没有构建链 = 改完刷新就生效，部署时就是一个静态目录。一个人的项目，**少一个 npm 依赖就少一个半夜挂掉的理由**；
- 目标用户是手机浏览器，原生 JS 完全够用（打包后整个前端不到 30KB）。

**代价**：状态管理靠一个全局 `state` 对象，列表刷新是全量重渲染。单页几十条数据无感；如果列表上千条，就该考虑虚拟滚动或者换框架了。

## 7. 为什么通知只做「站内红点」，不接微信/QQ 推送

接推送需要：公众号/小程序资质、模板消息审核、用户授权、回调验签、access_token 维护——**任何一项都能让一个学生项目卡住两周**。

而"站内红点"解决的是 80% 的需求：谁接了我的单、我的单被取走了，打开页面一眼看到。剩下的 20%（"我不打开页面就不知道"）用最原始的方式补：**宿舍群里还有嘴**。

这一条写在这里，是为了提醒自己：**功能取舍的标准是"目标用户会不会因此不用它"，不是"技术上能不能实现"。**

---

## 8. 明确不做的功能

| 功能 | 不做的理由 |
| --- | --- |
| 地图导航到快递点 | 校园里就那几个点，写"菜鸟驿站"比一个地图 pin 更省事 |
| 在线支付悬赏 | 涉及资金就是另一类合规问题；"一杯奶茶"是社交货币，不是订单 |
| 原生 App | 手机浏览器足够；上架还要开发者账号和审核 |
| 多宿舍/多校区 | 一期只需要证明"6 个人真的在用"，不需要证明"能服务一万个宿舍" |
| 管理后台 | 没有需要管理的人——房间是自组织的 |

---

## 9. 已知的不足（诚实清单）

- **没有自动化测试覆盖并发**：乐观锁的正确性靠 SQL 语义保证，但没写并发压测脚本；
- **身份靠 cookie，不防伪造**：知道别人 member id 就能冒充。在"6 个熟人"的威胁模型下接受；
- **没有数据备份机制**：SQLite 单文件，删了就没了。上云后需要加定时备份；
- **前端无错误重试**：网络抖动时列表可能空白，需要手动刷新。

这些不是"忘了做"，是**在当前目标下的主动欠账**，写清楚比藏着好。
